# Phase 6: Practical Testing Guide on the VM

This guide breaks down exactly how to practically execute **Phase 6** testing on the shared VM. Testing on the VM proves that the deployment, infrastructure, and integrations are robust under production conditions.

> [!IMPORTANT]
> All commands and verifications below must be executed **on the shared VM**, either via SSH or by pointing your local test scripts at the VM's public IP/Domain.

---

## 1. VM Deployment & Service Resilience
**Goal:** Prove the services are running, accessible, and can survive crashes.

### Step 1.1: Verify Uptime
Run Docker Compose checks to ensure all containers are healthy.
```bash
docker compose ps
docker compose logs --tail=50 control-plane
```
**Acceptance:** All containers show as `Up` (or `healthy`), and logs show no immediate startup tracebacks.

### Step 1.2: Restart Recovery & Resilience (Chaos Testing)
Manually kill a critical service and ensure the system recovers without losing state.
```bash
# Kill the decision brain container
docker kill pravah-decision-brain

# Wait 10 seconds, then check if Docker auto-restarted it (if using restart policies)
# or start it back up manually
docker compose start decision-brain
```
**Acceptance:** The service re-initializes, successfully reconnects to Redis/MASTERDB, and resumes processing tasks.

---

## 2. TANTRA & MASTERDB Integration (End-to-End)
**Goal:** Prove that an execution flows entirely through the system and hits MASTERDB.

### Step 2.1: Trigger Live Execution
Use `curl` or Postman to hit the VM's PRAVAH endpoint and trigger a full TANTRA execution cycle.
```bash
curl -X POST http://<VM_IP>:7000/api/execute \
  -H "Content-Type: application/json" \
  -d '{"signal": "test_signal", "metadata": {"source": "phase6_test"}}'
```

### Step 2.2: Verify MASTERDB Certification
Check the MASTERDB database or logs to ensure it registered the event.
**Acceptance:** The event must have a `trace_id`, a `validation_score`, and a successful certification status logged in MASTERDB.

### Step 2.3: Verify Bucket Integration
If your TANTRA pipeline writes artifacts to a bucket, verify the file exists on the VM.
```bash
ls -la data/bucket/
# or check your cloud bucket if using S3
```

---

## 3. Telemetry Generation & Trace Continuity
**Goal:** Prove that observability data is being generated for ML systems.

### Step 3.1: Inspect the Telemetry Log
Check the raw JSON logs being generated by PRAVAH on the VM.
```bash
tail -n 20 logs/control_plane/append_only_log.jsonl
```
**Acceptance:** Look for the following fields in the JSON output:
- `request_latency`
- `trace_id`
- `execution_duration`
- `validation_score`

### Step 3.2: Trace Continuity
Pick one `trace_id` from the log above and grep for it across all service logs.
```bash
docker compose logs | grep "<YOUR_TRACE_ID>"
```
**Acceptance:** The exact same `trace_id` should appear in the logs for `control-plane`, `decision-brain`, and your TANTRA components, proving continuity.

## 4. Replay Compatibility
**Goal:** Prove the system can perfectly reconstruct past states using the telemetry log.

### Step 4.1: Run Replay Verification
Run your existing Phase 3 verification script on the VM against the live production logs.
```bash
# Run this inside the control-plane container, or natively if Python is configured on the VM
python scripts/verify_phase3.py
```
**Acceptance:** The script should output `✓ Hash chain verification: PASSED` and `✓ FULL LINEAGE VERIFICATION: PASSED`, proving the live telemetry is replay-ready.

---

## 5. Concurrent Request Handling
**Goal:** Prove the VM deployment doesn't collapse under load.

### Step 5.1: Load Testing
Use a tool like `ab` (Apache Bench) or a Python script to spam the VM with concurrent requests.
```bash
# Example using Apache Bench: Send 500 requests, 20 at a time
ab -n 500 -c 20 -p test_payload.json -T application/json http://<VM_IP>:7000/api/execute
```
**Acceptance:** 
- The system handles the load without dropping connections (Zero 502/503 errors).
- Gunicorn/Uvicorn workers successfully distribute the load.
- No `Errno 22` or socket exhaustion errors appear in the logs.
